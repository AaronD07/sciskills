# Running the frontier science tasks

The manifest selects 12 development tasks and 16 holdouts from Terminal-Bench-Science v0.1.0. Each task belongs to one split. Four holdouts are marked for the smaller transfer sample. The task IDs, upstream Git trees and registry digests were recorded before model evaluation. The original tasks cover different scientific workflows, including estimating a lake's ice season, reconstructing a traffic-flow law, calibrating a watershed model and interpreting orbital measurements. [Upstream release](https://github.com/harbor-framework/terminal-bench-science/tree/v0.1.0)

From the repository root, run these commands with Python 3.11 or newer, Git and Docker.

```sh
python3 -m benchmarks.research_review.frontier list --phase dev
python3 -m benchmarks.research_review.frontier status --phase all
python3 -m benchmarks.research_review.frontier preflight --phase dev --task mendota-ice-phenology
python3 -m benchmarks.research_review.frontier preflight --phase dev
```

Cloning and building images need network access. The participant, reference and grading containers have no external network access. Two development tasks rely on the upstream fabricator or public evaluator. Each runs in a separate container on the participant’s isolated loopback interface with the original hostname. Service state resets between first drafts. The adapter rejects a review fork of either development task because committing its filesystem would lose live instrument state. All 16 holdouts use filesystem snapshots without a sidecar. Set `SCISKILLS_TBS_SOURCE` to change the checkout path or `SCISKILLS_TBS_STATE` to change the control receipt directory. The checkout must match the manifest's commit, and selected task directories must be clean. Both Dockerfiles and all inputs come from those directories. Image builds may take several minutes. Some reference solutions and verifiers are CPU intensive.

For a verifier that needs more RAM than the participant engine, run preflight with `SCISKILLS_TBS_VERIFIER_CONTEXT` set to a second local Docker context. The adapter copies the verifier image, verifies its immutable image ID, and records the participant and verifier context names and Docker engine IDs. Fresh controls are required when changing participant contexts. Scoped receipts allow independently qualified engines to coexist. Run a draft and every fork of that draft in the same participant context. Its snapshot is a local image there. Grades use the verifier context recorded for that participant’s controls. The AMR verifier requests 12 GiB. The project used a separate 4-CPU, 24-GiB Colima VM for that verifier. An operating-system kill is recorded as unscored even if the upstream shell writes a zero for the interrupted process.

Preflight grades the untouched participant, runs the published solution in that participant, and grades its artifacts. Each grade uses a fresh verifier container. A task becomes eligible only when the untouched environment fails and the published solution receives the full upstream reward of 1. Building images or obtaining a partial reference score cannot qualify a case. Each receipt records the exact participant and verifier image IDs; the runner reuses those images. The status command prints shareable counts and image IDs, including the grouped CTRF count and the complete pytest result when available. A saved snapshot is in `frontier_controls.json`. Receipts live under `benchmark-runs/research-review/frontier-controls/` by default and contain private verifier diagnostics. The TESS and masked remapping verifiers use native system-call filters or a filesystem jail, so those two tasks use native ARM64 images on ARM64 Docker engines. The finite free Stam proof task also uses the host architecture. Its upstream Dockerfiles pin a Lean toolchain for both platforms. On the local ARM64 engine, the official proof timed out under AMD64 emulation and passed all nine checks natively within the original 600-second verifier budget. The remaining tasks use the upstream Dockerfiles built for Linux AMD64.

Participants see the original instructions and the files in the original environment. Reviewers start from separate copies of the same committed first-draft image. After a session ends the adapter transfers only the artifact paths declared in the original task configuration into a clean verifier. It executes the upstream test script there and retains the scalar reward and component counts. None of the hidden tests, oracle files or prior grades are passed to reviewers. A missing required submission is recorded separately from a verifier that could not return a reward. Submitted archives with links, device entries or special permission bits are recorded as unsupported. A timed-out verifier, an unsupported archive or a failed reference control cannot establish a model mistake.

These runs use the published scientific tasks and verifiers with a different agent harness, network policy and machine. In particular, tasks whose original evaluator measures runtime can be sensitive to architecture and concurrent load. Treat the measurements as results for the selected cases and runner. The suite's version and file digests make it possible to repeat the same selection elsewhere.

When tasks qualify on different local engines, run `python3 -m benchmarks.research_review.dispatch holdout` after sealing, then run the same command with `reviews`. The dispatcher saves one verified participant engine per task, and every model and review of that task uses that engine. Pass `--tasks` to run a fully verified subset early. Set `--parallel-tasks` and `--workers-per-task` to fit the machine. Start admission checks the Docker VM’s available memory before starting the model clock. The default reserve is 2,650 MiB and can be set with `SCISKILLS_LAUNCH_RESERVE_MIB`. Each study worker rechecks the engine and immutable source image before grading a saved snapshot.
